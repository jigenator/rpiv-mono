## Why findings remain

### MLflow/OpenTelemetry: 24 findings (4 high, 20 moderate)

`packages/rpiv-telemetry` is private but remains a production workspace dependency. It depends on `@mlflow/core ~0.2.0`, which depends on `@opentelemetry/sdk-node ^0.205.0`. This is an implemented, opt-in MLflow tracing feature, not an abandoned dependency. No features were removed.

`extension.ts` does not import the heavy barrel. `providers/index.ts` imports the MLflow provider dynamically only when `providers.mlflow` is configured in `$XDG_CONFIG_HOME/rpiv-telemetry/config.json` (default `~/.config/rpiv-telemetry/config.json`). With no providers configured it is inert. `trackingUri` in that provider config or `MLFLOW_TRACKING_URI` must also be present before SDK initialization succeeds. Environment variables alone do not enable the provider. The root git-package Pi manifest exposes only the questionnaire, not telemetry. These loading boundaries reduce exposure; they do not eliminate the shipped vulnerable production dependency tree.

Latest `@mlflow/core` 0.4.0 still requires `sdk-node ^0.205.0`; upgrading MLflow alone cannot fix the chain (and increases unpacked size from ~222 KB to ~19.9 MB). An override to the first fully fixed `sdk-node`, 0.220.0, was evaluated and rejected after API/source review: 0.205 creates no metric reader when `OTEL_METRICS_EXPORTER` is unset, whereas 0.220 defaults unset/empty to OTLP. MLflow calls `new NodeSDK({ spanProcessors: [processor] })` without `metricReaders`, so that override would add default metrics export/network activity. Constructor/start/shutdown signatures still exist, but their relevant defaults are not behavior-compatible. The override was removed before final validation; no MLflow/SDK source was changed. An export smoke for that rejected configuration was deliberately not used to justify shipping it.

Follow-up requires explicit MLflow SDK setup with `metricReaders: []` or an approved `OTEL_METRICS_EXPORTER=none` policy before upgrading, followed by in-memory init/span-export/flush/shutdown tests. Do not blindly override the SDK or remove telemetry.

### Pi shrinkwrap: 5 findings (3 high, 2 moderate)

Pi is a root **dev dependency**, not a direct runtime dependency. Workspace `*` peer dependencies nevertheless make it production-reachable under npm's default peer installation, so all five appear in the root `--omit=dev` audit. The actual legacy-peer scratch install omits Pi entirely and does not include these five.

`@earendil-works/pi-coding-agent 0.80.6` includes `npm-shrinkwrap.json`: its nested undici 8.5.0, brace-expansion 5.0.6, protobufjs 7.6.4 and zod 3.25.76 remain pinned. Root overrides cannot reliably replace shrinkwrapped dependencies; no ineffective overrides or shrinkwrap edits were added. `npm audit fix` advertises fixes but does not change these pins. A trial upgrade of all Pi dev pins/legacy aliases to 1.4.0 produced **136 TypeScript errors** involving branded transcript/JSON types and new `ExtensionToolContext.tools/executeTool`. All Pi version changes were reverted rather than migrating runtime/test sources. Latest Pi 1.4.0 also shrinkwraps vulnerable undici 8.10.2, so upgrading alone is not a zero-audit solution.

Follow-up: a source-compatible, security-fixed Pi parent release or separately approved Pi API migration/upstream shrinkwrap repair.
